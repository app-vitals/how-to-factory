# Cursor: lesson 6 review grid (how review findings are graded and filtered)

Scope: lesson 6 only, the quality of a review: how findings are graded, what keeps weak ones off the PR, what the reviewer reads
for guidance, what each finding must show, how a repeat review behaves, how a person says a finding is wrong, how noise is
counted, and whether the reviewer states a verdict. Left out on purpose: what triggers a review and who fixes the PR afterwards
(lesson 4, see `landscape/routing-grid/cursor.md`) and how work is checked before the PR (lesson 3, see
`landscape/verify-grid/cursor.md`). Every filled cell is a paraphrase of a first-party cursor.com page, with its URL and the
date I fetched it (**2026-11-11**). The two files above were a starting list; every page used here was fetched again.

Names are Cursor's own, not canonical. A cell says `not documented` only after naming the pages checked, and that wording means
only that those pages do not say it; it is not a claim about the product.

Method: fetched the docs index (https://cursor.com/docs/llms.txt, 2026-11-11), listed every page that could touch review,
Bugbot, Autofix, rule files, approval, analytics or the changelog, and downloaded each docs page as raw Markdown (the `.md`
form of its URL). The pages in the first block of "Pages read" were read in full. The blog and changelog pages are HTML
pages; I read them through a page-extraction tool that returns a summary against a question, not the raw text, so those are
partial reads and each claim from them is limited to what the extraction returned (see "Pages read"). The main changelog
index page was fetched but not usable as text, so I used the dated Bugbot changelog entry instead.

Surfaces: **Bugbot** (the PR reviewer), **Bugbot Autofix** (a cloud agent that fixes what Bugbot found), and a **third group of
nearby surfaces**: Agent Review (review of local changes inside the editor), PR Routing & Approval (the one that approves) and
the Agent SDK review templates (build-your-own reviewers).

## The grid

| Dimension | Bugbot | Bugbot Autofix | Nearby: Agent Review, PR Routing & Approval, SDK templates |
| --- | --- | --- | --- |
| **Findings graded by severity or confidence** | Severity yes, in data: the review analytics API returns a `severity` per finding (the doc's examples show `high` and `medium`); the scale and its meaning are not defined on the page, and the field can be null. Confidence as a visible grade on a comment: not documented (checked: Bugbot docs, Bugbot help page, Bugbot blog posts). Rules can ask for a finding to be "blocking" or "non-blocking" in the rule's own wording (examples on the Bugbot page). ([Bugbot](https://cursor.com/docs/bugbot.md), 2026-11-11) | Not documented as its own grading (checked: Bugbot docs). A changelog entry says Autofix now triggers only for substantial findings, which implies a bar but does not describe it. ([Changelog 2026-04-08](https://cursor.com/changelog/04-08-26), 2026-11-11) | Security Agents list findings with a severity of critical, high or medium in their API. Agent Review has two depths (Quick, Deep), a cost and speed choice, not a grade. SDK review templates are one comment each, and what counts as a finding is whatever you write in the template's instructions. ([Security Agents](https://cursor.com/docs/security-agents.md), [Agent Review](https://cursor.com/docs/agent/agent-review.md), [Review templates](https://cursor.com/docs/agent-sdk/templates/reviews.md), 2026-11-11) |
| **Threshold or cap on how many comments post** | No cap on a count of comments: not documented (checked: Bugbot docs, Bugbot help page). Caps that exist are on whether a review runs: a PR over a default size limit (changed lines and diff characters) is skipped with a comment asking to split it, and a team has a default cap on how many reviews run on PRs opened by bot accounts. Generated files (marked `linguist-generated`) are left out and do not count toward size. The review effort setting (Low, Default, High, Smart) trades cost and time against how many bugs it may find. ([Bugbot](https://cursor.com/docs/bugbot.md), 2026-11-11) | On "Commit to Existing Branch" it makes at most 3 attempts per PR, to avoid loops. A count cap on findings it addresses: not documented (checked: Bugbot docs). ([Bugbot](https://cursor.com/docs/bugbot.md), 2026-11-11) | An SDK review template posts one comment per run, via a single findings call. ([Review templates](https://cursor.com/docs/agent-sdk/templates/reviews.md), 2026-11-11) |
| **Verification or filter pass before posting** | The Bugbot docs and help page do not describe the internal pipeline (checked both). A Cursor blog post on improving Bugbot says it runs eight passes over the diff with the diff order shuffled, keeps only bugs found in more than one pass (majority vote), then sends survivors through a validator model for false positives, filters out unwanted categories (examples named: compiler warnings, documentation errors) and removes ones already posted in earlier runs. The post describes results through January 2026, so the pipeline may have changed since. ([Building a better Bugbot](https://cursor.com/blog/building-bugbot), 2026-11-11) | The fix is made by a cloud agent in an isolated machine that tests as it works; whether it re-verifies the finding first: not documented (checked: Bugbot docs, Autofix blog post). The Autofix post lists letting Bugbot verify its own findings as future work. ([Bugbot Autofix blog](https://cursor.com/blog/bugbot-autofix), 2026-11-11) | PR Routing & Approval waits for the Bugbot and Security Agent checks on the latest commit (up to about 8 minutes) and will not approve if they report findings needing a human. Vulnerability Remediation sends each scanner finding to a verification agent that writes exploit tests; findings it shows are not vulnerabilities land in an "Agent-refuted" tab. ([PR Routing & Approval](https://cursor.com/docs/approval-agents.md), [Security Agents](https://cursor.com/docs/security-agents.md), 2026-11-11) |
| **Filter for problems that existed before the PR** | Not documented as a filter (checked: Bugbot docs, Bugbot help page, Bugbot blog posts). Nearby facts: it analyzes the PR diff, and by default only the changes since its previous review. ([Bugbot](https://cursor.com/docs/bugbot.md), 2026-11-11) | Not documented (checked: Bugbot docs). | Security Agents split the job by when code is checked: Security Review looks at PRs before merge, and Vulnerability Remediation scans code at rest for existing problems. ([Security Agents](https://cursor.com/docs/security-agents.md), 2026-11-11) |
| **Repo guidance files it reads, and how it is told what to ignore** | `.cursor/BUGBOT.md`: the root file is always included, and files in directories above changed files are added, so nested ones apply to their subtree. Files linked from a BUGBOT.md count as separate rules. Team rules set in the dashboard, learned rules and manual repository rules (with optional path globs) are merged into one block (team, then BUGBOT.md, then learned, then manual). Each rule is cut at 30,000 characters and the total at 100,000. Cursor's own `.cursor/rules/*.mdc` files do not apply to Bugbot. "What to ignore" is prose inside these rule files; the structural exclusions are generated files and a repo-level `.cursor/config/bugbot.yaml` (triggers, effort, incremental, summary, autofix mode), read from the PR's base branch so a PR cannot change its own review settings. Commenting `bugbot run verbose=true` posts a table of the rules used and any truncated. Credential-like files (`.env`, keys, `*.tfvars`, Terraform state) are not read. ([Bugbot](https://cursor.com/docs/bugbot.md), [Bugbot help](https://cursor.com/help/ai-features/bugbot.md), 2026-11-11) | Follows the findings it is given; a guidance file specific to Autofix: not documented (checked: Bugbot docs). The config file's `autofix.mode` can only lower the dashboard's Autofix mode, not raise it. ([Bugbot](https://cursor.com/docs/bugbot.md), 2026-11-11) | Agent Review also reads `BUGBOT.md` files. PR Routing & Approval reads `APPROVAL_POLICY.md` (exact name, from the changed file's directory and each ancestor) and `.cursor/approval-policies/ROUTING.md`; if a PR edits a policy file, the base-branch version is used, or a human is required. SDK templates keep their rules in the template's own `bot/instructions.md`. ([Agent Review](https://cursor.com/docs/agent/agent-review.md), [PR Routing & Approval](https://cursor.com/docs/approval-agents.md), [Review templates](https://cursor.com/docs/agent-sdk/templates/reviews.md), 2026-11-11) |
| **Evidence required (file and line)** | A rule that every finding must cite a location: not documented (checked: Bugbot docs, Bugbot help page). What the pages show: comments are inline on the PR with an explanation and a suggested fix; in dry-run mode each finding is returned with a title, a description and locations that include file, start line and end line. ([Bugbot](https://cursor.com/docs/bugbot.md), [Bugbot help](https://cursor.com/help/ai-features/bugbot.md), 2026-11-11) | It posts a comment on the PR with the outcome and pushes the fix to a branch (new or existing). ([Bugbot](https://cursor.com/docs/bugbot.md), 2026-11-11) | Not documented (checked: Agent Review, Review templates). |
| **Re-review: only new changes, no repeat of earlier comments** | By default it reviews only changes since its previous review; turning off "Incremental Review" reviews the whole diff on each push. It reads earlier PR comments, top-level and inline, to avoid duplicate suggestions. A "once per PR" setting skips later commits entirely. A diff already reviewed in the editor with `/review-bugbot` (matched by git patch ID) is skipped, with a comment saying so. ([Bugbot](https://cursor.com/docs/bugbot.md), 2026-11-11) | Not documented as separate behavior (checked: Bugbot docs). The 3-attempt limit applies per PR. | Not documented (checked: Agent Review, Review templates). |
| **How a person dismisses it or teaches it a finding is wrong** | Reply `@cursor remember [fact]` on a PR and Bugbot saves it as a learned rule for later reviews. Learned rules are also built automatically from merged or closed PRs, and per the learning blog post the signals are a downvote reaction, a developer reply, and comments a human reviewer made on things Bugbot missed; rules that keep getting negative signal are disabled automatically, and rules can be edited or deleted in the dashboard. The blog gives no thresholds. Marking a thread resolved: the Bugbot page uses "resolved" status for findings, but what a person clicks to dismiss is not described (checked: Bugbot docs, Bugbot help). ([Bugbot](https://cursor.com/docs/bugbot.md), [Bugbot learned rules blog](https://cursor.com/blog/bugbot-learning), 2026-11-11) | Set Autofix to Off and use the manual "Fix in Cursor" or "Fix in Web" links, or pick a mode (new branch is the recommended one). ([Bugbot](https://cursor.com/docs/bugbot.md), 2026-11-11) | In PR Routing & Approval a person can edit the custom prompt or policy files; Security Agents findings can be `dismissed` (API status). ([PR Routing & Approval](https://cursor.com/docs/approval-agents.md), [Security Agents](https://cursor.com/docs/security-agents.md), 2026-11-11) |
| **How its own noise is measured** | A **resolution rate** is Cursor's headline measure: an AI judge decides, when the PR merges, which flagged bugs the author actually fixed in the final code. Blog posts report it rising from 52% to over 70%, then to about 78% as of 2026-04-08; these are Cursor's own figures, not independent. Per rule, the dashboard shows issues found, PRs reviewed, accepted issues and an acceptance rate. The team analytics API returns per review: findings count, per finding `resolution_status` and `severity`, billed cost, and per PR counts of issues and how many were resolved. A false-positive rate by that name: not documented (checked: Bugbot docs, analytics API page, the blog posts). A dry-run mode runs the whole analysis without posting, so findings can be read first. ([Bugbot](https://cursor.com/docs/bugbot.md), [Analytics API](https://cursor.com/docs/account/teams/analytics-api.md), [Building a better Bugbot](https://cursor.com/blog/building-bugbot), [Bugbot learned rules blog](https://cursor.com/blog/bugbot-learning), 2026-11-11) | A merge rate: the Autofix blog reports over 35% of Autofix changes are merged into the PR (Cursor's own figure, at the time of that post). The GitHub check `Cursor Bugbot Autofix` reports only success or neutral. ([Bugbot Autofix blog](https://cursor.com/blog/bugbot-autofix), [Bugbot](https://cursor.com/docs/bugbot.md), 2026-11-11) | Security Agents track vulnerabilities found, issues fixed and a resolution rate; an LLM reads later diffs to decide whether a flagged issue was fixed. ([Security Agents](https://cursor.com/docs/security-agents.md), 2026-11-11) |
| **Does it state a verdict or approve** | A status is published per run: GitHub check `Cursor Bugbot`. `success` means no findings and no unresolved comments from earlier runs; `neutral` means findings (the default), a run cancelled by a newer commit, or an internal error; `failure` only if "fail on unresolved issues" is configured and available to the org. It never emits `skipped`. Requiring the check in branch protection makes Bugbot run before merge but does not block on findings unless it is set to fail. Whether Bugbot itself submits an approving review: not documented (checked: Bugbot docs, Bugbot help). ([Bugbot](https://cursor.com/docs/bugbot.md), 2026-11-11) | A separate check that is only `success` or `neutral`. ([Bugbot](https://cursor.com/docs/bugbot.md), 2026-11-11) | **PR Routing & Approval** can approve low-risk PRs, using a risk score, a maximum risk level, policy files and the Bugbot and Security findings; it does not approve while those report issues needing a human, and says it does not replace a full review (GitHub and Origin repos only). The SDK GitHub guide's example posts its decision as a review through the GitHub API. ([PR Routing & Approval](https://cursor.com/docs/approval-agents.md), [Agent SDK GitHub guide](https://cursor.com/docs/agent-sdk/guides/github.md), 2026-11-11) |

## Findings worth carrying into the lesson

- Grading is mostly implicit in the docs: severity exists as a data field, while the filtering that keeps weak findings off the PR is described only in a blog post (multiple passes, majority vote, validator model, category filter, dedupe against earlier runs). ([Building a better Bugbot](https://cursor.com/blog/building-bugbot), [Bugbot](https://cursor.com/docs/bugbot.md), 2026-11-11)
- The guidance file is `.cursor/BUGBOT.md`, nested by directory, and it is separate from the editor's own rules files; "ignore" is prose. Settings that control behavior are read from the base branch. ([Bugbot](https://cursor.com/docs/bugbot.md), 2026-11-11)
- Teaching is a loop: reply to remember a fact, plus rules learned from reactions, replies and human comments, with automatic disabling of rules that attract negative signal. ([Bugbot](https://cursor.com/docs/bugbot.md), [Bugbot learned rules blog](https://cursor.com/blog/bugbot-learning), 2026-11-11)
- Noise is measured as a resolution rate (was the flagged bug fixed by merge), not a false-positive rate, plus acceptance rate per rule. ([Bugbot](https://cursor.com/docs/bugbot.md), [Building a better Bugbot](https://cursor.com/blog/building-bugbot), 2026-11-11)
- The default verdict is a neutral check, so "Bugbot ran" and "Bugbot blocks" are separate settings. ([Bugbot](https://cursor.com/docs/bugbot.md), 2026-11-11)
- No pre-existing-problem filter, no hard comment-count cap and no must-cite-a-line rule is described in the pages named in the cells above. These are gaps in the docs, not a statement about the product.
