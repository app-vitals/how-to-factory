# Factory (Droid Review): review grid

Scope: how Factory's code review decides which findings to show, meaning how findings are graded, how many post, what
filters run before posting, what repository files steer it, what evidence a finding carries, how a re-review behaves, how a
person pushes back, how its own noise is measured, and whether it states a verdict. Left out on purpose: how work is
verified before a PR (see `landscape/verify-grid/factory.md`), plans (see `landscape/plan-grid/factory.md`), and
sandbox or permission design.
Every filled cell is a paraphrase of a first-party page, with its URL and the date I fetched it (**2026-11-11**). Names are
Factory's own (Droid Review, Droid Action, `review-guidelines` skill), not canonical.

Method: fetched the docs index (https://docs.factory.com/llms.txt, 2026-11-11), listed every page that could touch review
quality (local `/review`, Automated Code Review, Security Review, automations, AGENTS.md, skills, the review benchmark,
agent effectiveness, compliance, the changelog), then fetched the raw Markdown (`<url>.md`) of each with `curl`, so the
text was read directly and not through a summary. Started from `landscape/routing-grid/factory.md` and
`landscape/verify-grid/factory.md`, but every page was fetched again; their notes are not carried over unchecked.

## The grid

Surfaces: **Local `/review`** (interactive command in a Droid session), **CI review** (Droid Action on pull requests, also
called Droid Review), **Security review** (separate skill, local or in CI), **PR Reviewer automation** (a scheduled starter in
Automations).

| Surface | Dimension | Value | Source | As of |
| --- | --- | --- | --- | --- |
| Local `/review` | severity grading | Every finding carries a priority from P0 (blocks release) to P3 (nice to have). The rubric says what to do at each level: P0 fix before merge, P1 fix before the work counts as done, P2 fix when practical, P3 only if nearby work makes it fit | https://docs.factory.com/automations/code-review | 2026-11-11 |
| CI review | severity grading | Not documented for code review on this page (checked: automations/code-review-ci). The inline comments are described only as feedback on problematic lines. The P0 to P3 scale appears on the local `/review` page, and Security review uses it as Critical to Low | https://docs.factory.com/automations/code-review-ci ; https://docs.factory.com/automations/security-review | 2026-11-11 |
| Security review | severity grading | Four levels, each tied to a priority: Critical (P0), High (P1), Medium (P2), Low (P3), with example vulnerability types per level. A severity-threshold input exists but its details live in the action's `action.yml`, which I did not read (outside the Factory host allowlist) | https://docs.factory.com/automations/security-review | 2026-11-11 |
| Local `/review` | confidence grading | Not documented as a score (checked: automations/code-review, automations/code-review-ci, automations/security-review). Confidence shows up only as a gate: a bug is flagged only when it meets every item of an eight-point test (see "pre-existing" and "verification" rows) | https://docs.factory.com/automations/code-review | 2026-11-11 |
| CI review | threshold or cap on posted comments | No default cap is documented. The page shows how to add one: put a line in the prompt such as "submit at most 5 comments total, prioritizing the most critical issues". Draft PRs are skipped, and a paths filter or a skip condition on the workflow can keep whole PRs or files out | https://docs.factory.com/automations/code-review-ci | 2026-11-11 |
| CI review | what it looks for and what it skips | Aims at clear defects: unreachable code, broken control flow, async mistakes, null dereferences, leaks, injection, missing error handling, off-by-one, races. Says it skips style, minor optimisation and architecture opinions | https://docs.factory.com/automations/code-review-ci | 2026-11-11 |
| Local `/review` | verification or filter pass before posting | Not documented as a separate pass (checked: automations/code-review, automations/code-review-ci). The only gate is the eight-point test a finding must pass to count as a bug: real impact, discrete and fixable, no more rigour than the rest of the code, caused by the change, worth the author's time, based on fact not guess, tied to specific affected code, and not a deliberate choice | https://docs.factory.com/automations/code-review | 2026-11-11 |
| Security review | verification or filter pass before posting | Yes, two passes. First candidates are generated by tracing changed data flows; then each candidate is re-checked for reachability, exploitability, existing controls and false positives before it is reported. Only findings with a realistic exploit path are reported | https://docs.factory.com/automations/security-review | 2026-11-11 |
| Local `/review` | filter for problems that existed before the PR | Yes, as one of the eight tests: a finding must be introduced by the reviewed changes, not already present. The review is taken against the merge base of the chosen base branch | https://docs.factory.com/automations/code-review | 2026-11-11 |
| CI review | filter for problems that existed before the PR | Not documented on this page (checked: automations/code-review-ci). It says the review fetches the PR diff and existing comments. The introduced-by-the-change test is documented for local `/review` only | https://docs.factory.com/automations/code-review-ci ; https://docs.factory.com/automations/code-review | 2026-11-11 |
| CI review | repo guidance file it reads | `.factory/skills/review-guidelines/SKILL.md`; its text is injected into every review run with no workflow change. Example content is a list of extra checks for the codebase. It applies to code review only | https://docs.factory.com/automations/code-review-ci | 2026-11-11 |
| Security review | repo guidance file it reads | `.factory/skills/security-review-guidelines/SKILL.md`, a separate skill from the code-review one; a rule wanted in both must be written in both. Its rules take priority over the built-in methodology where they conflict, and are passed to every subagent. If `.factory/threat-model.md` exists it is used as the attack-surface map. The guidelines file is treated as untrusted input: a rule asking to send findings out, write outside the audit folder, run destructive commands or skip consent gates is ignored | https://docs.factory.com/automations/security-review | 2026-11-11 |
| CI review | how it is told what to ignore | Three documented routes: a paths list in the workflow trigger (the example skips `**/*.test.ts`), a job condition that skips bot PRs or a title tag such as `[skip-review]`, and the guidelines skill. For security review the example guideline text tells it not to report command injection under an internal-scripts folder. Whether `AGENTS.md` is read by the reviewer: not documented (checked: harness/agents-md, automations/code-review-ci; the AGENTS.md page lists "review checks" only as something a team may write in) | https://docs.factory.com/automations/code-review-ci ; https://docs.factory.com/automations/security-review ; https://docs.factory.com/harness/agents-md | 2026-11-11 |
| Local `/review` | evidence required (file and line) | File path and line number are part of each finding "when applicable"; a short reason says why it matters and what triggers it. Each finding is one paragraph with an imperative title of 80 characters or fewer and code snippets of at most three lines. A concrete fix is attached only when safe and specific | https://docs.factory.com/automations/code-review | 2026-11-11 |
| CI review | evidence required (file and line) | Findings are inline comments on the lines concerned, and an optional setting (default on) adds code suggestion blocks. A rule requiring proof beyond that: not documented | https://docs.factory.com/automations/code-review-ci | 2026-11-11 |
| CI review | re-review behaviour | The workflow runs again on each push to the PR (the synchronize event) and on reopen or ready-for-review. It reads the existing comments before reviewing. Whether it reviews only the new commits or avoids repeating earlier comments: not documented (checked: automations/code-review-ci, automations/security-review) | https://docs.factory.com/automations/code-review-ci | 2026-11-11 |
| PR Reviewer automation | re-review behaviour | The starter checks every 30 minutes on weekdays from 9:00 to 17:00 and posts one review comment per head commit, so a new push gets a new comment | https://docs.factory.com/automations/custom | 2026-11-11 |
| CI review | how a person dismisses a finding or teaches it | Not documented as a feedback control (checked: automations/code-review-ci, automations/security-review, automations/code-review). The documented lever is editing the guidelines skill or the workflow. A comment-driven helper exists for fixing, not for teaching: the Review Comment Fixer starter acts on a teammate's PR comment by pushing one commit | https://docs.factory.com/automations/code-review-ci ; https://docs.factory.com/automations/custom | 2026-11-11 |
| Review (any) | how its own noise is measured | A Review Benchmark page exists, titled as results and methodology for review models, but its Markdown holds only an embedded component, so no figures or method can be read from it. Agent Effectiveness measures throughput, output and cost attribution, with no review-comment acceptance or false-positive figure on the pages read | https://docs.factory.com/benchmarks/review-benchmark ; https://docs.factory.com/agent-effectiveness/overview ; https://docs.factory.com/agent-effectiveness/dashboard | 2026-11-11 |
| Local `/review` | states a verdict | Yes: ends with an overall assessment saying whether the changes are correct or incorrect, plus one to three sentences | https://docs.factory.com/automations/code-review | 2026-11-11 |
| CI review | states a verdict or approves | Yes: it submits an approval when it finds no issues. When it finds issues it posts inline comments. Whether it ever requests changes or blocks a merge: not documented (checked: automations/code-review-ci, automations/security-review); the compliance page advises the team to require PR reviews through branch protection | https://docs.factory.com/automations/code-review-ci ; https://docs.factory.com/enterprise/compliance-audit-and-monitoring | 2026-11-11 |
| CI review | depth and model | One setting picks the preset: `deep` (default, slower, costlier, aimed at production code) or `shallow` (faster, surface issues). Factory keeps each preset on a current model; per-model overrides are possible but discouraged | https://docs.factory.com/automations/code-review-ci | 2026-11-11 |

## Not documented (with pages checked)

- A confidence score on a code-review finding: automations/code-review, automations/code-review-ci, automations/security-review.
- A default cap on the number of CI review comments (only a prompt line that adds one): automations/code-review-ci.
- A separate verification pass for code review, as opposed to security review: automations/code-review,
  automations/code-review-ci.
- A pre-existing-problem filter for CI review: automations/code-review-ci (the test is stated for local `/review`).
- Whether a re-review looks only at new changes or avoids repeating earlier comments: automations/code-review-ci,
  automations/security-review, automations/custom.
- A way for a person to dismiss a finding so the reviewer learns from it: the same three pages plus
  automations/code-review.
- Whether the reviewer reads `AGENTS.md`: harness/agents-md, automations/code-review-ci, harness/skills.
- Any measured noise or false-positive rate for Droid Review: benchmarks/review-benchmark (component only),
  agent-effectiveness/overview, agent-effectiveness/dashboard, agent-effectiveness/cost-and-productivity.

## Ruled out (why)

- **github.com/Factory-AI/droid-action (`action.yml`, setup docs)**: first-party code, but github.com is not on Factory's
  allowlist in `landscape/matrix.json`; the docs pages name its inputs, and the unread inputs (severity threshold,
  blocking, bot allowlists) are marked as such above. First place to look if those gaps matter.
- **Review Benchmark figures**: rendered by a component and absent from the Markdown; not recorded rather than guessed.
- **Docs for Bitbucket, GitLab and Azure DevOps setup**: same review behaviour as GitHub per the CI page; platform setup only.
- **CVE remediation, Incident Response, Triage**: not code review of a PR.
- **Enterprise, pricing, models, BYOK, audit log**: not review quality (compliance read only for the branch-protection advice).
- **`/deep-review` skill**: appears only in a changelog line; no page describes it, so it is not described here.
