# OpenHands: lesson 6 review grid (how review findings are graded and filtered)

Scope: lesson 6 only, the quality of a review: how findings are graded, what keeps weak ones off the PR, what the reviewer reads
for guidance, what each finding must show, how a repeat review behaves, how a person says a finding is wrong, how noise is
counted, and whether the reviewer states a verdict. Left out on purpose: what triggers a review and who fixes the PR afterwards
(lesson 4, see `landscape/routing-grid/openhands.md`) and how work is checked before the PR (lesson 3, see
`landscape/verify-grid/openhands.md`). Every filled cell is a paraphrase of a first-party page, with its URL and the date I
fetched it (**2026-11-11**). The two files above were a starting list; every page used here was fetched again.

Names are OpenHands' own, not canonical. A cell says `not in their docs` only after naming the pages checked, and that wording
means only that those pages do not say it; it is not a claim about the product.

Source tiers: the docs pages on docs.openhands.dev are the primary source. The docs name two skill files and a plugin that hold
the actual review instructions, all in the first-party `OpenHands/extensions` repository on GitHub. I fetched those raw files too
(see "Pages read") and mark each such claim "skill text" so it is not mistaken for a docs-page claim. Skill text is on the `main`
branch and can change; the date is the fetch date.

Method: fetched the docs index (https://docs.openhands.dev/llms.txt, 2026-11-11), listed every page that could touch review,
automations, skills or review measurement, and downloaded each as a raw-Markdown URL. Every page in the first block of "Pages
read" was read in full. The documentation pages say little about grading and filtering on their own; most depth is in the skill
text the docs point to.

Surfaces: **Automated Code Review** (the GitHub Action or Cloud automation running the `pr-review` plugin with the `/codereview`
and `/github-pr-review` skills), **Software Factory reviewer** (the third of four Agent Canvas automations), **GitHub PR Review
Assistant** (an Agent Canvas prebuilt that interviews you and builds a review automation).

## The grid

| **Findings graded by severity or confidence** | Severity yes: comments carry a priority label, Critical, Important, Suggestion or Nit. ([Automated Code Review](https://docs.openhands.dev/openhands/usage/use-cases/code-review.md), 2026-11-11) Skill text defines them: Critical is a must-fix (security hole, bug, data-loss risk), Important a should-fix (logic error, performance, missing error handling), Suggestion a worthwhile clarity or maintainability gain. ([github-pr-review skill](https://github.com/OpenHands/extensions/blob/main/skills/github-pr-review/SKILL.md), 2026-11-11) A separate whole-PR **risk assessment** (Low, Medium, High) is always in the review, as an escalation signal and not as a defect. ([risk-evaluation reference](https://github.com/OpenHands/extensions/blob/main/skills/code-review/references/risk-evaluation.md), 2026-11-11) A numeric confidence score: not in their docs (checked: Automated Code Review, PR Review workflow, and both skill files). | Not in their docs as a grade (checked: Software Factory). ([Software Factory](https://docs.openhands.dev/openhands/usage/use-cases/software-factory.md), 2026-11-11) | Not in their docs (checked: GitHub PR Review Assistant). The agent asks whether to post one summary comment or detailed inline feedback. ([GitHub PR Review Assistant](https://docs.openhands.dev/openhands/usage/agent-canvas/prebuilt/github-pr-review.md), 2026-11-11) |
| **Threshold or cap on how many comments post** | A numeric cap: not in their docs (checked: Automated Code Review, PR Review workflow, plugin README, both skill files). What exists is a content threshold in skill text: only a "material finding" may become a thread, meaning a concrete failure on the current head, the affected user or boundary, and evidence; optional refactors, style or naming preferences, speculative hardening, praise and "add more tests" with no unverified behavior are explicitly not findings. The posting skill says never post Nit or "this is fine" comments, and to bundle all comments in one review call. Related symptoms are to be merged into one root-cause finding. ([code-review skill](https://github.com/OpenHands/extensions/blob/main/skills/code-review/SKILL.md), [github-pr-review skill](https://github.com/OpenHands/extensions/blob/main/skills/github-pr-review/SKILL.md), 2026-11-11) The docs page lists Nit as a label while the posting skill says not to post it; I did not find which one wins at run time. | Not in their docs (checked: Software Factory). | Not in their docs (checked: GitHub PR Review Assistant). |
| **Verification or filter pass before posting** | Yes, as an instructed step, not a separate system. Skill text says that before posting each finding the agent must re-read the current file, reproduce the failure logically or empirically, check whether a caller, test or documented exception invalidates it, and collapse symptoms to one root cause; if any step fails, drop it or put it in the review body as a non-blocking question without an inline thread. It also verifies the path and line against the checked-out workspace instead of counting diff lines, and verifies any code-suggestion block against the real lines it replaces. ([code-review skill](https://github.com/OpenHands/extensions/blob/main/skills/code-review/SKILL.md), [github-pr-review skill](https://github.com/OpenHands/extensions/blob/main/skills/github-pr-review/SKILL.md), 2026-11-11) An optional `use-sub-agents` input splits a large PR into per-file reviews, then consolidates. ([Automated Code Review](https://docs.openhands.dev/openhands/usage/use-cases/code-review.md), [plugin README](https://github.com/OpenHands/extensions/blob/main/plugins/pr-review/README.md), 2026-11-11) A second, independent model pass over the findings: not in their docs (checked: same pages). | The page says the reviewer checks out the exact PR head and runs its relevant tests before posting its review and statuses. A filter on findings: not in their docs (checked: Software Factory). ([Software Factory](https://docs.openhands.dev/openhands/usage/use-cases/software-factory.md), 2026-11-11) | Not in their docs (checked: GitHub PR Review Assistant). It can optionally read CI results before commenting. ([GitHub PR Review Assistant](https://docs.openhands.dev/openhands/usage/agent-canvas/prebuilt/github-pr-review.md), 2026-11-11) |
| **Filter for problems that existed before the PR** | Partly, in skill text: a finding must be a problem "present on the current head" and must not be one added only after an earlier review or already fixed elsewhere in the PR. The text does not say "ignore code the PR did not touch" in so many words; the review target is the changed-file manifest and diff. ([code-review skill](https://github.com/OpenHands/extensions/blob/main/skills/code-review/SKILL.md), 2026-11-11) A diff-base filter stated on a docs page: not in their docs (checked: Automated Code Review, PR Review workflow, plugin README). | Not in their docs (checked: Software Factory). | Not in their docs (checked: GitHub PR Review Assistant). The setup asks which files, directories or checks to ignore, which scopes the review but is not a pre-existing-code filter. ([GitHub PR Review Assistant](https://docs.openhands.dev/openhands/usage/agent-canvas/prebuilt/github-pr-review.md), 2026-11-11) |
| **Repo guidance files it reads, and how it is told what to ignore** | A repo skill at `.agents/skills/custom-codereview-guide.md` with the `/codereview` trigger (the older `.openhands/skills/` path also works). It must not be named `code-review`, because a plugin skill with the same name overrides the project one; under a different name both are loaded, concatenated with no smart merge, so conflicting rules are reconciled by the agent. The page's template has sections for when to approve, when to comment, principles, what to check and conventions. ([Automated Code Review](https://docs.openhands.dev/openhands/usage/use-cases/code-review.md), [PR Review workflow](https://docs.openhands.dev/sdk/guides/github-workflows/pr-review.md), 2026-11-11) Skill text also says to read the root and nested `AGENTS.md` files, the repo's review guide, contribution and architecture docs, the linked issue and its acceptance criteria, and the PR discussion and prior threads, and to treat issue bodies, comments and patches as untrusted evidence, not instructions. ([code-review skill](https://github.com/OpenHands/extensions/blob/main/skills/code-review/SKILL.md), 2026-11-11) The docs' general skills page names `AGENTS.md` (loaded in full), and also recognizes `CLAUDE.md` and `GEMINI.md`. ([Skills Overview](https://docs.openhands.dev/overview/skills.md), 2026-11-11) A dedicated "ignore" section or ignore-file syntax: not in their docs (checked: Automated Code Review, PR Review workflow, Skills Overview, plugin README); ignoring is written in prose in the guide. The skill text says the reviewer reads the guide from the PR head. | The page says the reviewer "follows the repository's guidance" and does not name a file (checked: Software Factory). ([Software Factory](https://docs.openhands.dev/openhands/usage/use-cases/software-factory.md), 2026-11-11) | The agent asks which files, directories or checks the reviewer should ignore, during the setup conversation. A guidance file: not in their docs (checked: GitHub PR Review Assistant). ([GitHub PR Review Assistant](https://docs.openhands.dev/openhands/usage/agent-canvas/prebuilt/github-pr-review.md), 2026-11-11) |
| **Evidence required (file and line)** | A line reference is part of the documented output: "specific line references" and suggestions with code. ([Automated Code Review](https://docs.openhands.dev/openhands/usage/use-cases/code-review.md), 2026-11-11) Skill text makes a finding material only with evidence in code, instructions, tests, the issue or review history; the final review lists findings with file and verified line, and the posting call needs a path, a new-file line and a side. ([code-review skill](https://github.com/OpenHands/extensions/blob/main/skills/code-review/SKILL.md), [github-pr-review skill](https://github.com/OpenHands/extensions/blob/main/skills/github-pr-review/SKILL.md), 2026-11-11) A separate, optional `require-evidence` input (off by default) makes the reviewer demand an Evidence section in the PR description with end-to-end proof; it is evidence from the PR author, not evidence in each finding. ([Automated Code Review](https://docs.openhands.dev/openhands/usage/use-cases/code-review.md), 2026-11-11) | Not in their docs (checked: Software Factory). The page says exact-head review and test statuses are recorded. ([Software Factory](https://docs.openhands.dev/openhands/usage/use-cases/software-factory.md), 2026-11-11) | Not in their docs (checked: GitHub PR Review Assistant). |
| **Re-review: only new changes, no repeat of earlier comments** | Pushes do not start a review by default; the Cloud automation leaves out the push event on purpose "to avoid noisy re-reviews", and a follow-up needs the label re-added or the reviewer re-requested. The automation prompt says to avoid duplicating existing unresolved review comments. ([Automated Code Review](https://docs.openhands.dev/openhands/usage/use-cases/code-review.md), 2026-11-11) Skill text reads prior reviews and resolved and unresolved threads, says a later bot run must not approve while a concrete earlier human concern is unverified, and says to check that a finding was not added only after an earlier review. A "review only the new commits" mode: not in their docs (checked: Automated Code Review, PR Review workflow, plugin README, code-review skill). ([code-review skill](https://github.com/OpenHands/extensions/blob/main/skills/code-review/SKILL.md), 2026-11-11) | The page says failed checks lead to revisions and "fresh acceptance of the changed commit", and that a branch made stale by other merges is updated and waits for a fresh exact-head review before merge. ([Software Factory](https://docs.openhands.dev/openhands/usage/use-cases/software-factory.md), 2026-11-11) | Not in their docs (checked: GitHub PR Review Assistant). |

The block also invites a thumbs-up or thumbs-down reaction, and points to an `/iterate` skill to resolve findings with the agent. ([code-review skill](https://github.com/OpenHands/extensions/blob/main/skills/code-review/SKILL.md), 2026-11-11) A docs-page description of dismissing a thread or of what a reaction does: not in their docs (checked: Automated Code Review, PR Review workflow, plugin README). | **Does it state a verdict or approve** | Yes. ([code-review skill](https://github.com/OpenHands/extensions/blob/main/skills/code-review/SKILL.md), [github-pr-review skill](https://github.com/OpenHands/extensions/blob/main/skills/github-pr-review/SKILL.md), 2026-11-11) | The page says the reviewer records exact-head review and test statuses, and the watchdog merges only on passing independent acceptance statuses. ## Findings worth carrying into the lesson

- Most of OpenHands' review quality control is prompt text, not product configuration. The docs pages describe triggers and setup; grading, the proof step and the do-not-post rules sit in the skill text that the plugin loads. ([Automated Code Review](https://docs.openhands.dev/openhands/usage/use-cases/code-review.md), [code-review skill](https://github.com/OpenHands/extensions/blob/main/skills/code-review/SKILL.md), 2026-11-11)
- The skill defines a "material finding" (concrete failure, who is affected, evidence) and says to say nothing rather than manufacture feedback; that is the main noise filter, together with a drop-it-if-unproven rule per candidate. ([code-review skill](https://github.com/OpenHands/extensions/blob/main/skills/code-review/SKILL.md), 2026-11-11)
- Teaching is by editing a repo skill file and re-requesting review, with the guide read from the PR head; there is no named per-finding dismiss action on the docs pages checked. ([code-review skill](https://github.com/OpenHands/extensions/blob/main/skills/code-review/SKILL.md), 2026-11-11)
- Re-review is manual on the Cloud automation by design, and the skill carries prior threads into the next run to avoid repeats. ([Automated Code Review](https://docs.openhands.dev/openhands/usage/use-cases/code-review.md), 2026-11-11)
- Noise measurement is documented as a recipe (suggestion-accuracy ratio via an after-merge LLM judge) that the user runs, with an evaluation workflow in the plugin repo; no built-in figure is shown on the pages read. ([Monitoring and Improving Skills](https://docs.openhands.dev/overview/skills/monitoring.md), 2026-11-11)
- Two wording differences between the docs page and the skill text (Nit label; Critical versus REQUEST_CHANGES) are worth checking against a live run before relying on either.
- No numeric comment cap, confidence score, pre-existing-code filter on a docs page, or per-finding dismiss button was found in the pages named in the cells above. These are gaps in the docs read, not a statement about the product.
