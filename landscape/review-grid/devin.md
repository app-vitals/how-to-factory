# Devin: lesson 6 review grid (how review findings are graded and filtered)

Scope: lesson 6 only, the quality of a review: how findings are graded, what keeps weak ones off the PR, what the reviewer reads
for guidance, what each finding must show, how a repeat review behaves, how a person says a finding is wrong, how noise is
counted, and whether the reviewer states a verdict. Left out on purpose: what triggers a review and who fixes the PR afterwards
(lesson 4, see `landscape/routing-grid/devin.md`) and how work is checked before the PR (lesson 3, see
`landscape/verify-grid/devin.md`). Every filled cell is a paraphrase of a first-party docs.devin.ai page, with its URL and the
date I fetched it (**2026-11-11**). The two files above were a starting list; every page used here was fetched again.

Names are Devin's own, not canonical. A cell says `not documented` only after naming the pages checked, and that wording means
only that those pages do not say it; it is not a claim about the product.

Method: fetched the docs index (https://docs.devin.ai/llms.txt, 2026-11-11) and the Cloud and API section indexes
(https://docs.devin.ai/_llms/en/cloud.txt, https://docs.devin.ai/_llms/en/api.txt), listed every page that could touch review,
bots, instruction files, findings, scans or review analytics, and downloaded each as a raw-Markdown URL. The pages in the first
block of "Pages read" were read in full. The 2026 release-notes page is 4,277 lines; I searched it for review terms and read
only the matching entries, so it is a partial read (see "Pages read").

Surfaces: **Devin Review** (the PR reviewer: Bug Catcher, security scan), **Custom reviewers** (beta, named checks you write),
**Autoapprover** (beta, approve or leave for a person), **Auto-Fix on a Devin-owned PR** (findings triaged before posting).

## The grid

| Dimension | Devin Review (Bug Catcher and security scan) | Custom reviewers and Autoapprover (beta) | Auto-Fix on a Devin-owned PR |
| --- | --- | --- | --- |
| **Findings graded by severity or confidence** | Yes, two ways. Bugs are **Severe** (described as high-confidence, needing immediate attention) or **Non-severe**. Security findings are **Critical** (high-confidence, fix before merge) or **Warning**, with a CWE id where one applies. Flags are a separate class: **Investigate** (look closer) and **Informational** (explains or notes correctness). The Auto-Fix gallery page says bugs are labelled by severity and by confidence; the Review page gives no confidence scale beyond the Severe wording. ([Devin Review](https://docs.devin.ai/work-with-devin/devin-review.md), [Auto-Fix PR Bugs](https://docs.devin.ai/use-cases/gallery/devin-review-autofix.md), 2026-11-11) | A custom reviewer carries one urgency chosen by whoever writes it: **Severe**, **Moderate** or **Info**; every finding it posts gets that urgency and the reviewer's name. Autoapprover grades nothing per finding; it reads the review's findings with a rubric of intent, code quality and incident risk. ([Devin Review](https://docs.devin.ai/work-with-devin/devin-review.md), 2026-11-11) | Not documented as its own grading (checked: Devin Review, Auto-Fix PR Bugs). The findings arrive with the grades in the first cell. |
| **Threshold or cap on how many comments post** | No cap on a count of comments: not documented (checked: Devin Review, Auto-Fix PR Bugs, GitHub integration). What exists is a switch per finding type: bugs and security are posted by default; investigate flags and informational flags are not, and an admin can turn each on or off. A per-repository override can pick other categories, including none. This sets what is posted, not whether the review runs. ([Devin Review](https://docs.devin.ai/work-with-devin/devin-review.md), 2026-11-11) | Not documented (checked: Devin Review). A reviewer with no matching rule does not run; a draft or disabled one does not run either. | Findings Devin could not fix are posted; fixed ones are listed in a status on the PR instead. No count cap documented (checked: Devin Review). ([Devin Review](https://docs.devin.ai/work-with-devin/devin-review.md), 2026-11-11) |
| **Verification or filter pass before posting** | A separate verification step by name: not documented (checked: Devin Review, Auto-Fix PR Bugs, Devin PR bot comment settings). The page says Bugs are the findings the Bug Catcher has high confidence in, and that later reviews check for duplicate and already-resolved findings. Whether that is a pass before the first post is not stated. ([Devin Review](https://docs.devin.ai/work-with-devin/devin-review.md), 2026-11-11) | Not documented (checked: Devin Review). | Yes, for accounts that have "direct finding triage" turned on: the session that opened the PR works through the findings first, fixes what it can, records its decisions, and only the rest are posted. It needs a running or suspended session that created the PR, not one that took it over. Availability varies by account and provider, per the page. ([Devin Review](https://docs.devin.ai/work-with-devin/devin-review.md), 2026-11-11) |
| **Filter for problems that existed before the PR** | Not documented as a filter (checked: Devin Review, Auto-Fix PR Bugs). Two nearby facts: for a later push it looks for bugs "introduced or affected by" the changes since the last review, and each PR in a stack is diffed against the layer below so a review sees only that layer. ([Devin Review](https://docs.devin.ai/work-with-devin/devin-review.md), 2026-11-11) | Not documented (checked: Devin Review). A reviewer's written instructions can say what to ignore; that is guidance, not a filter on old code. | Not documented (checked: Devin Review). |
| **Repo guidance files it reads, and how it is told what to ignore** | Reads, as context: `**/REVIEW.md`, `**/AGENTS.md`, `**/CLAUDE.md` and `**/CONTRIBUTING.md` (case-insensitive), `.cursorrules`, `.windsurfrules`, `.cursor/rules`, `*.rules`, `*.mdc`, `.coderabbit.yaml` or `.yml`, and `greptile.json`. A file under `.agents/`, `.devin/`, `agents/`, `.cursor/` or `.github/` counts as belonging to the parent directory. `REVIEW.md` is the review-specific one; the page's example has an "Ignore" section (generated files, lock files) and the gallery page's example tells it not to flag one named hook. Extra file globs can be added in Settings > Review under Context, and a beta lets admins write central review instructions. Security instructions in these files steer the security scan. Exclusions in the rules say which PRs are not reviewed at all (by author type, label, title, branch, changed files or diff size). ([Devin Review](https://docs.devin.ai/work-with-devin/devin-review.md), [Auto-Fix PR Bugs](https://docs.devin.ai/use-cases/gallery/devin-review-autofix.md), 2026-11-11) | A custom reviewer takes plain-text instructions ("what to check and what to ignore") or follows a repository or organization skill; a repository skill is read from the default branch. Autoapprover reads `APPROVAL_POLICY.md` from the repo root and from the directories of changed files, taken from the target branch, so a PR cannot write its own approval rules; a PR that edits one needs a person. ([Devin Review](https://docs.devin.ai/work-with-devin/devin-review.md), 2026-11-11) | The session follows the repo's own instruction files as for any session (see the AGENTS.md page). The page for review does not name a file for this surface. ([AGENTS.md files for Devin](https://docs.devin.ai/onboard-devin/agents-md.md), 2026-11-11) |
| **Evidence required (file and line)** | A hard rule that every finding must cite a location: not documented (checked: Devin Review, Auto-Fix PR Bugs). What the pages show: a finding's "Learn more" holds an explanation, a concrete example and a recommended fix; the copy button copies the finding with its location; the gallery example is a Severe bug naming a file and line (`UserSettings.tsx:38`) with a fix commit. Security findings include a description and a fix recommendation. ([Devin Review](https://docs.devin.ai/work-with-devin/devin-review.md), [Auto-Fix PR Bugs](https://docs.devin.ai/use-cases/gallery/devin-review-autofix.md), 2026-11-11) | Findings carry the reviewer's name and urgency; whether they must carry a line: not documented (checked: Devin Review). Autoapprover shows its result and its reasoning in the PR's Autoapprover section. ([Devin Review](https://docs.devin.ai/work-with-devin/devin-review.md), 2026-11-11) | The status on the PR lists what was fixed; the fix lands as a commit, shown in the gallery example. ([Auto-Fix PR Bugs](https://docs.devin.ai/use-cases/gallery/devin-review-autofix.md), 2026-11-11) |
| **Re-review: only new changes, no repeat of earlier comments** | On a push to an already-reviewed PR it usually looks at the changes since the last review, carries earlier findings forward and checks whether the new commits fixed them. If the PR's purpose changed a lot, or the new diff is too large for an incremental pass, it can review the whole PR again. On later reviews it checks for duplicate and resolved findings rather than treating all as new. A later push is only reviewed automatically if the rule's cadence is "Every push"; otherwise "Only once". ([Devin Review](https://docs.devin.ai/work-with-devin/devin-review.md), 2026-11-11) | Autoapprover re-evaluates enrolled PRs on every push, using the previous decision plus the new changes, with a full reassessment when needed; it can withdraw an earlier approval if a later evaluation changes its mind. Custom reviewers: re-run behavior not documented (checked: Devin Review). ([Devin Review](https://docs.devin.ai/work-with-devin/devin-review.md), 2026-11-11) | The "No Issues Found" summary is always ignored; only comments with real findings start Auto-Fix. ([Devin Review](https://docs.devin.ai/work-with-devin/devin-review.md), [Devin PR bot comment settings](https://docs.devin.ai/product-guides/bot-comment-settings.md), 2026-11-11) |
| **How a person dismisses it or teaches it a finding is wrong** | A person marks a bug, flag or security finding **resolved**; resolved items dim and sort to the bottom, and when every thread of a bot review is resolved Devin minimizes that review on GitHub (and restores it if a thread is reopened). Teaching it: edit `REVIEW.md` (the gallery page suggests adding the pattern that would have caught a production bug), or add a line such as "do not flag X". Chat on a finding can ask a follow-up. A feedback button or thumbs-down that trains the reviewer: not documented (checked: Devin Review, Auto-Fix PR Bugs, 2026 release notes search for dismiss, feedback and false). ([Devin Review](https://docs.devin.ai/work-with-devin/devin-review.md), [Auto-Fix PR Bugs](https://docs.devin.ai/use-cases/gallery/devin-review-autofix.md), 2026-11-11) | Edit the reviewer's instructions or its rules and exclusions; the run history shows counts of fixed and ignored findings. ([Devin Review](https://docs.devin.ai/work-with-devin/devin-review.md), 2026-11-11) | Under the default bot setting Devin ignores comments from bot accounts, and Devin Review posts as `devin-ai-integration[bot]`, so the session does not act on its own review's comments until that bot is allowed. ([Devin PR bot comment settings](https://docs.devin.ai/product-guides/bot-comment-settings.md), 2026-11-11) |
| **How its own noise is measured** | Per repository, the consumption dashboard shows review ACUs, review count and number of bugs caught (Enterprise). A release note of 2026-10-21 says review analytics now count a finding as resolved only when it was fixed in code, by a later push or by Devin; findings a reviewer dismissed and duplicates no longer count. A false-positive or precision rate: not documented (checked: Devin Review, 2026 release notes search, PR Metrics API). The PR Metrics API returns only counts of PRs opened, closed and merged. ([Devin Review](https://docs.devin.ai/work-with-devin/devin-review.md), [2026 release notes](https://docs.devin.ai/release-notes/2026.md), [PR Metrics](https://docs.devin.ai/api-reference/v2/consumption/pr-metrics.md), 2026-11-11) | Per custom reviewer, the run history shows fixed and ignored finding counts. ([Devin Review](https://docs.devin.ai/work-with-devin/devin-review.md), 2026-11-11) | Not documented (checked: Devin Review, Auto-Fix PR Bugs). |
| **Does it state a verdict or approve** | Two pieces. A `Devin Review` commit status is posted by default, and its passing condition is chosen by an admin: review completed (default), threads resolved, or no findings; posting a check does not make it a merge requirement unless branch rules require it. Comments a person writes in Devin Review go out under their own identity, and commits and comments are never made for a user unless that user starts the action. ([Devin Review](https://docs.devin.ai/work-with-devin/devin-review.md), 2026-11-11) | **Autoapprover** (beta) posts a real approval of the reviewed commit or leaves the PR for a person; the page warns that an approval can satisfy a repo requirement and let auto-merge or a merge queue proceed, and that it does not merge. Custom reviewers can be a separate check (`Devin Review / <name>`) with the same three passing conditions. ([Devin Review](https://docs.devin.ai/work-with-devin/devin-review.md), 2026-11-11) | Not documented (checked: Devin Review, Auto-Fix PR Bugs). |

## Findings worth carrying into the lesson

- Grading lives in two places: a severity on every bug and security finding (Severe or Non-severe, Critical or Warning), and a posting switch per class, so low-grade classes (investigate and informational flags) are shown in the app but not posted by default. ([Devin Review](https://docs.devin.ai/work-with-devin/devin-review.md), 2026-11-11)
- The guidance file is `REVIEW.md`, with a long list of other agent and rule files read as context; "ignore" is written in prose in that file, not as a separate config. ([Devin Review](https://docs.devin.ai/work-with-devin/devin-review.md), 2026-11-11)
- Re-review is incremental by default, with findings carried forward and duplicates checked, and a full re-review only when the change is large or its purpose shifts. ([Devin Review](https://docs.devin.ai/work-with-devin/devin-review.md), 2026-11-11)
- The one measured-noise change documented is on what counts as "resolved": only fixed-in-code, not dismissed. ([2026 release notes](https://docs.devin.ai/release-notes/2026.md), 2026-11-11)
- No dedicated pre-existing-problem filter, count cap, verification pass or thumbs-down learning loop is described in the pages named in the cells above. These are gaps in the docs, not a statement about the product.
